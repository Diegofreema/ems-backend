# ltalms REST API

A stateless JSON API layered on top of the existing CakePHP web app. It runs
**alongside** the web UI without changing it — the web app keeps using session
login; the API uses tokens.

- **Base URL:** `/api/v1`
- **Format:** JSON only (`Content-Type: application/json`)
- **Auth:** JWT bearer tokens (user context) **or** API key + secret (server-to-server)
- **Controllers:** `src/Controller/Api/`
- **Routes:** the `Api` prefix scope in `config/routes.php`

## Response envelope

Success:
```json
{ "success": true, "data": { ... }, "meta": { "page": 1, "limit": 25, "total": 7, "pages": 1 } }
```
Error:
```json
{ "success": false, "message": "Human readable reason", "errors": { "field": { "_required": "..." } } }
```
`meta` appears only on list endpoints. `errors` appears only on validation (422) failures.

## Authentication

### 1. User login (JWT)
```
POST /api/v1/auth/login
{ "username": "chukwudi@example.com", "password": "secret" }
```
Returns an `access_token` (1h) and a `refresh_token` (30d):
```json
{ "success": true, "data": {
  "token_type": "Bearer",
  "access_token": "eyJ...",
  "expires_in": 3600,
  "refresh_token": "eyJ...",
  "user": { "id": 1, "username": "...", "role_id": 5, "status": "Enabled" }
}}
```
Send the access token on every request:
```
Authorization: Bearer eyJ...
```

### 2. Refresh
```
POST /api/v1/auth/refresh
{ "refresh_token": "eyJ..." }
```

### 3. Who am I
```
GET /api/v1/auth/me
Authorization: Bearer eyJ...
```

### 4. Server-to-server API keys
Admins (role 1/5/7) mint keys for trusted backend integrations:
```
POST /api/v1/auth/api-keys
Authorization: Bearer <admin token>
{ "name": "Reporting Service" }
```
Returns `api_key` and `api_secret` **once**. The secret is stored hashed and
cannot be retrieved again. Use them via headers:
```
X-Api-Key: lk_xxx
X-Api-Secret: yyy
```
API-key clients are treated as trusted and bypass per-role checks (except the
few endpoints explicitly restricted to real users, e.g. student delete).

**Roles:** `1`, `5`, `7` = admin/super-admin · `2` = student · `3` = teacher · `4` = parent.

## Students (pilot resource)

| Method | Path | Description | Access |
|--------|------|-------------|--------|
| GET | `/api/v1/students` | List (filters + search + pagination) | any authenticated |
| GET | `/api/v1/students/{id}` | Single student (full detail) | any authenticated |
| POST | `/api/v1/students` | Create | admin / API key |
| PUT/PATCH | `/api/v1/students/{id}` | Update | admin / API key |
| DELETE | `/api/v1/students/{id}` | Delete | admin users only |
| GET | `/api/v1/students/lookup?regno=` | Find by registration number | any authenticated |
| GET | `/api/v1/students/{id}/results` | Student's results | any authenticated |
| GET | `/api/v1/students/{id}/invoices` | Student's invoices | any authenticated |
| GET | `/api/v1/students/{id}/transactions` | Student's transactions | any authenticated |

**List filters** (query string): `department_id`, `class_arm_id`, `level_id`,
`session_id`, `status`, `studentstatus`, `gender`, `q` (free text over
name/regno/email), `page`, `limit` (max 100).

Example:
```
GET /api/v1/students?department_id=1&status=Admitted&q=chukwudi&page=1&limit=25
Authorization: Bearer eyJ...
```

## Generic resources (Phase 2+)

These resources share a uniform REST interface generated by `Api\CrudController`.
Every one supports the same operations and query parameters:

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/{resource}` | List (filter + search + sort + paginate) |
| GET | `/api/v1/{resource}/{id}` | View one (with belongsTo relations) |
| POST | `/api/v1/{resource}` | Create (admin / API key) |
| PUT/PATCH | `/api/v1/{resource}/{id}` | Update (admin / API key) |
| DELETE | `/api/v1/{resource}/{id}` | Delete (admin users) |

**Common query params:** any column as `?column=value` (exact match) · `?q=`
(free-text over name fields) · `?sort=column&direction=asc|desc` · `?page=` ·
`?limit=` (max 100).

**Available resources so far** (dashed URLs for multi-word names):

- Phase 1: `students`
- Phase 2: `teachers`, `employees`, `subjects`, `departments`, `class-arms`,
  `levels`, `sessions`, `semesters`, `faculties`, `courses`, `sparents`
- Phase 3: `results`, `assignments`, `setassignments`
- Phase 4: `fees`, `invoices`, `transactions`, `payslips`, `sponsorships`,
  `spendings`, `sponsorshippayments`, `feeallocations`, `paylogs`, `donations`
- Phase 6: `books`, `borrowedbooks`, `coursematerials`, `eresources`
- Phase 7: `news`, `notifications`, `staffmessages`, `studentmessages`,
  `letters`, `subcategory`, `votes`, `topics`, `trequests`, `couriers`
  - `POST /news/{id}/publish` / `POST /news/{id}/unpublish` (status live/offline)
  - (posts, comments, forum, postcategories, muteds tables absent → not routed)
- Phase 8 (reference/lookup + remaining, bulk CRUD): `admins`, `admins-privileges`,
  `admisionconditions`, `approvedresults`, `cafcredit`, `candidates`, `categories`,
  `constants`, `countries`, `courseassignments`, `courseassignments-subjects`,
  `courseregistrations`, `courseregistrations-subjects`, `departments-fees`,
  `departments-levels`, `departments-programes`, `departments-programmes`,
  `departments-semesters`, `departments-subjects`, `fees-levels`, `fees-students`,
  `lgas`, `logs`, `modes`, `positions`, `privileges`, `programes`, `programetypes`,
  `roles`, `settings`, `sparents-students`, `sponsors`, `sponsorships-students`,
  `staffdepartments`, `staffgrades`, `states`, `subjects-students`,
  `subjects-teachers`, `userlogins`, `users`
  - **Sensitive** (`users`, `admins`, `admins-privileges`, `privileges`,
    `userlogins`, `logs`, `settings`): reads are admin-only (roles 1/5/7) and
    API keys cannot write them. Passwords are never returned.
  - (fees-sponsorships, levels-subjects, semesters-subjects, sets tables absent → not routed)
- Phase 9 (hostel): `hostels`, `hostelrooms`, `hostelrooms-students`
  - `GET /hostelrooms/{id}/students` — a room's occupants
  - Assign a student to a room = `POST /hostelrooms-students { hostelroom_id, student_id }`; eject = `DELETE /hostelrooms-students/{id}`
  - (`employees` table absent — staff live in `teachers` — so `employees` is not routed)

**Total: 83 routed resources**, all verified returning `200`. Every remaining
web controller whose table is absent in this DB has its API controller written
but left unrouted, ready to enable if/when the table is created.
- Phase 5: `attendances`, `timetables`
  - `GET /attendances/roster?date=YYYY-MM-DD` — current teacher's class roster + existing marks
  - `POST /attendances/mark` — bulk save `{ attendance_date, records:[{student_id,status,notes}] }`
  - (admin_attendances, liveclasses, events tables don't exist in this DB → not routed)

Example:
```
GET /api/v1/teachers?department_id=1&q=john&sort=lastname&direction=asc&page=1&limit=20
Authorization: Bearer eyJ...
```

### Results — custom assessment endpoints (Phase 3)

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/results/transcript?student_id=` | All approved results for a student, ordered for transcript display |
| GET | `/api/v1/results/pending-approval` | Results awaiting approval (admin; accepts the usual filters) |
| POST | `/api/v1/results/{id}/approve` | Approve one (stamps `approved_by`/`approved_at`) |
| POST | `/api/v1/results/{id}/reject` | Reject one — body `{ "rejection_reason": "..." }` |
| POST | `/api/v1/results/approve-batch` | Approve many — body `{ "ids": [1,2,3] }` |
| POST | `/api/v1/results/reject-batch` | Reject many — body `{ "ids": [...], "rejection_reason": "..." }` |

`results` list filters: `student_id`, `subject_id`, `session_id`, `semester_id`,
`department_id`, `class_arm_id`, `level_id`, `faculty_id`, `regno`, `approval_status`.

**Setassignments** also expose `/setassignments/{id}/questions` and
`/setassignments/{id}/submissions`.

> **Feature not in this DB:** the exam & quiz tables (`exams`, `examquestions`,
> `quizzes`, `quizquestions`, `attemptedexamquestions`, `attemptedquizzes`) do
> not exist in the current `tss` database, so those resources are **not routed**
> (the controllers exist and can be enabled once the tables are created). The
> live CBT-taking and auto-grading engines from the web `Assignments`/
> `Setassignments` controllers are also not yet ported — CRUD + submissions
> listing are available; interactive test-taking is a later refinement.

### Finance notes (Phase 4)

- **Payment records** (`invoices`, `transactions`, `payslips`) are read-only to
  server-to-server API keys — only real authenticated users (JWT) can create or
  update them. Reads are open to both.
- Common web actions are covered by generic filters — no special endpoint needed:
  a student's invoices = `/invoices?student_id=`, pending payments =
  `/transactions?paystatus=initialized`, paid = `?paystatus=paid`, an employee's
  payslips = `/payslips?teacher_id=`.
- `fees` adds `POST /fees/{id}/activate` and `POST /fees/{id}/deactivate`
  (mirrors the web status toggle).
- **Not exposed:** payment-gateway initiation/verification (Paystack, Credo,
  Remita, Interswitch, Flutterwave) — these are browser-redirect callback flows,
  not REST endpoints. Bulk payroll generation is likewise not ported.

> **Known schema caveat:** a few models (e.g. `Semesters`, `Subjects`) declare
> belongsToMany associations to join tables that don't exist in the current `tss`
> database (`semesters_subjects`, `subjects_teachers`, …). Reads are unaffected,
> but a cascade **delete** on those resources fails with "table not found" — the
> same error the web app would raise. Create the missing join tables (or drop the
> stale association from the model) to enable delete on them.

## Quick test (curl)
```bash
# login
TOKEN=$(curl -s -X POST http://localhost/ltalms/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"USER","password":"PASS"}' | php -r 'echo json_decode(file_get_contents("php://stdin"),true)["data"]["access_token"];')

# list students
curl -s "http://localhost/ltalms/api/v1/students?limit=5" -H "Authorization: Bearer $TOKEN"
```

## Configuration

`config/app_local.php` → `Jwt` block:
```php
'Jwt' => [
    'secret'     => env('JWT_SECRET', '...'), // CHANGE in production
    'accessTtl'  => 3600,
    'refreshTtl' => 60 * 60 * 24 * 30,
    'issuer'     => 'ltalms-api',
],
```
Set a strong, random `JWT_SECRET` in production. The current default is a
placeholder committed to the repo and must not be used live.

## Security notes
- CORS is currently open (`Access-Control-Allow-Origin` echoes the request
  origin). Restrict `applyCors()` in `src/Controller/Api/AppController.php` to
  your known front-end origins before going to production.
- The API scope does **not** load CSRF/FormProtection — correct for a
  token-authenticated API, but it means every write endpoint MUST enforce auth
  (the base controller does this in `beforeFilter`).
- Rate limiting is not implemented; add it at the web server / reverse proxy.

See **API_ADDING_RESOURCES.md** for how to expose the remaining resources.
